# 08. 결과 검증 · 성공한 실행을 재현 가능한 결과로 만들기

**CH4~5 · 실행 상태와 결과 내용을 함께 검증하기.** 앞에서 수행한 모델 재로딩·Feast 조회·컴포넌트 연결 검증을 입력과 결과 파일 기준으로 정리한다. 클러스터 실행에서는 같은 기준에 단계 상태와 아티팩트 저장 확인을 더한다.

![예측 결과에서 입력과 모델 실행 근거를 추적하는 검증 구조](/images/week02-validation.svg)

## 1. 상태 성공과 내용 검증

| 확인 대상 | 상태가 알려주는 것 | 추가로 읽을 내용 |
|---|---|---|
| Pod Running | 컨테이너 실행 상태 | readiness·로그·실제 응답 |
| Job Complete | 작업이 성공 코드로 종료됨 | 비교표·모델 URI·assert 결과 |
| KFP 단계 Succeeded | 해당 작업의 실행 성공 | 실제 아티팩트 존재·내용 |
| 결과 파일 존재 | 저장 경로에 파일이 있음 | 행 수·스키마·키·예측값 |

kind의 MLflow 학습 Job은 Complete 1/1로 종료했고 등록 모델 재로딩 검사를 통과했다. 연결 검증에서는 Feast 조회와 네 컴포넌트의 파일 전달을 실행해 결과 150행과 예측 일치를 확인했다.

| 검증 대상 | 확인한 결과 |
|---|---|
| 등록 모델 재로딩 | 원래 모델과 같은 입력의 예측 일치 검사 통과 |
| Feast Historical 조회 | 평가 대상 150행의 피처가 원본 기준값과 일치 |
| Redis Online 조회 | 설비별 최신 관측 피처와 일치 |
| 컴포넌트 연결 | 입력 확인·조회·추론·저장 순차 실행 통과 |
| 최종 예측 비교 | 최대 절대 차이 약 1.42e-14 · 허용 오차 통과 |
| 파이프라인 정의 | KFP YAML 컴파일 통과 |

MLflow 실행은 kind에서, 피처·컴포넌트 연결 검증은 자동 실행 환경에서 확인했다. KFP 클러스터의 Run 상태와 MinIO 파일 입출력은 위 결과와 별도로 확인하는 항목이다.

## 2. 결과 파일과 실행 메타데이터

| 컬럼·메타데이터 | 목적 |
|---|---|
| equipment_id | 어떤 설비의 예측인지 식별 |
| prediction_timestamp | 어떤 시점의 예측인지 식별 |
| prediction | 회귀 모델의 품질 예측값 |
| model_uri / model_version | 실제 로드한 모델 버전 |
| MLflow run_id / KFP run_id | 실험과 실행의 원인 추적 |
| dataset hash / feature definition hash | 입력과 피처 정의 재현 |
| pipeline version | 처리 로직 변경 식별 |

현재 예측 CSV에는 Entity·예측 시각·예측값·모델 URI·학습 Run ID·데이터 해시를 남겼다. 파이프라인 버전은 결과를 기록하는 MLflow Run의 태그로 연결했다. 위 표의 피처 정의 해시와 KFP Run ID는 클러스터 실행·추적을 확장할 때 포함할 항목이다.

행별 컬럼과 파일 단위 메타데이터는 저장 형식에 맞게 나눌 수 있지만 연결 키를 보존해야 한다. 모델 입력에서는 Entity를 제외하더라도 최종 예측 결과에는 다시 붙인다. 행 순서만 믿고 결합하지 않고 Entity·시각 키와 join cardinality를 검사한다.

## 3. 동일 입력·동일 모델을 대조한 순서

1. MLflow의 `selection.json`에서 고정 모델 URI를 읽었다.
2. `test_predictions.csv`와 동일한 대상 행을 선택하고 데이터 해시와 피처 목록·순서를 검사했다.
3. Feast Historical 조회 결과를 원본의 동일 Entity·기준 시각 값과 대조했다.
4. 고정 모델로 추론 컴포넌트를 실행하고 Entity·시각으로 기존 예측과 결합했다.
5. 행 수·키 중복·결측을 검사한 후 예측값 차이를 허용 오차와 비교했다.

재로딩과 연결 검증 모두 `rtol=1e-10`, `atol=1e-10`의 assert를 사용했다. 이는 절대 오차만의 상한이 아니라 값의 크기에 따른 상대 허용 오차와 절대 허용 오차를 함께 적용하는 비교다. 모델이 같아도 입력 데이터가 다르면 예측값 차이를 모델 재로딩 문제로 해석할 수 없다.

## 4. 회귀 평가와 재현성은 다른 질문

예측값 일치는 같은 모델을 다시 사용했는지 확인한다. RMSE·MAE·R²는 정답과 비교한 예측 품질을 평가한다. 재로딩 차이가 0이어도 모델의 업무 성능이 충분하다는 뜻은 아니다. 우리 실습은 합성 회귀 데이터이므로 분류 교재 예제의 확률·임계값·accuracy를 그대로 결과 표에 넣지 않는다.

## 5. 재실행과 중복 처리

새 Run ID는 실행 추적에 유용하지만 같은 업무 요청의 중복 여부를 판단하는 키는 아니다. 예를 들어 설비·예측 시각·모델 버전·파이프라인 버전을 결과 키로 정하고, 동일 키의 재실행은 덮어쓸지 별도 이력으로 보관할지 정한다. 피처가 갱신될 수 있다면 피처 스냅샷 식별자도 포함한다.

## 6. 운영 확장으로 이어지는 질문

등록 모델 로딩이 끝난 뒤 Ready로 전환하는가? CPU 제한을 바꾸면 추론 지연이 어떻게 달라지는가? 메모리 부족 시 모델 Pod가 어떻게 복구되는가? 새 모델이 준비된 후 이전 모델을 내리고, 문제가 생기면 고정 버전으로 되돌릴 수 있는가?

이미 완료한 Probe·배포 전략·CPU·OOM·QoS 실습은 이 질문의 기반이다. 기존 관찰값은 [운영 자동화](/ml-platform/week-04)와 [리소스 관리](/ml-platform/week-05)에 보존한다. 실제 요청 연속 가용성이나 모델 추론 부하 측정값을 기존 Pod 상태 관찰로 대신하지 않는다.
